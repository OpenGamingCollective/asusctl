# asusd Configuration

`asusd` is the system daemon. Its configuration lives in `/etc/asusd/`, is owned by root, and is written by the daemon as state changes. Edit these files with `sudo`. Back up the directory before editing:

```bash
sudo cp -a /etc/asusd "/etc/asusd.bak.$(date +%F-%H%M%S)"
```

## Configuration files

| File | Purpose | Reload behaviour |
|---|---|---|
| `asusd.ron` | Platform profiles, battery charging, power commands, EPP, tuning, and Armoury settings. | Watched with inotify; changes are picked up while the daemon runs. |
| `fan_curves.ron` | Fan curves for the `balanced`, `performance`, `quiet`, and `custom` profiles. | Read at startup; restart `asusd.service` after editing. |
| `anime.ron` | AniMe Matrix display state and the system/boot/wake/shutdown sequences. | Read at startup; restart `asusd.service` after editing. |
| `scsi.ron` | SCSI drive LED state and the per-mode effects. | Read at startup; restart `asusd.service` after editing. |
| `slash.ron` | Slash LED bar state and the per-event display flags. | Read at startup; restart `asusd.service` after editing. |
| `aura_<product_id>.ron` | Generated Aura state for the detected keyboard. | Generated by `asusd`; do not edit by hand. |

## asusd.ron

The file is a single RON struct. A complete default file looks like this:

```ron
(
    charge_control_end_threshold: 100,
    base_charge_control_end_threshold: 100,
    disable_nvidia_powerd_on_battery: true,
    ac_command: "",
    bat_command: "",
    platform_profile_linked_epp: true,
    platform_profile_on_battery: Quiet,
    change_platform_profile_on_battery: true,
    platform_profile_on_ac: Performance,
    change_platform_profile_on_ac: true,
    profile_quiet_epp: Power,
    profile_balanced_epp: BalancePower,
    profile_custom_epp: Performance,
    profile_performance_epp: Performance,
    ac_profile_tunings: {},
    dc_profile_tunings: {},
    armoury_settings: {},
)
```

| Field | Type | Default | Description |
|---|---|---|---|
| `charge_control_end_threshold` | `u8` | `100` | Current battery charge limit percentage. Set it with `asusctl battery limit 80` (the accepted range is 20-100). |
| `base_charge_control_end_threshold` | `u8` | `100` | Charge limit restored after a one-shot full charge. `0` means "not set" for a config upgraded from an older version. |
| `disable_nvidia_powerd_on_battery` | `bool` | `true` | Stop `nvidia-powerd` while on battery and start it again on AC. |
| `ac_command` | `String` | `""` | Command run when AC power is connected. |
| `bat_command` | `String` | `""` | Command run when AC power is disconnected. |
| `platform_profile_linked_epp` | `bool` | `true` | Set the CPU energy-performance preference when the platform profile changes. |
| `platform_profile_on_battery` | `PlatformProfile` | `Quiet` | Profile applied when the laptop switches to battery. |
| `change_platform_profile_on_battery` | `bool` | `true` | Apply `platform_profile_on_battery` on the power-source change. |
| `platform_profile_on_ac` | `PlatformProfile` | `Performance` | Profile applied when AC power is connected. |
| `change_platform_profile_on_ac` | `bool` | `true` | Apply `platform_profile_on_ac` on the power-source change. |
| `profile_quiet_epp` | `CPUEPP` | `Power` | EPP value used for the Quiet profile. |
| `profile_balanced_epp` | `CPUEPP` | `BalancePower` | EPP value used for the Balanced profile. |
| `profile_custom_epp` | `CPUEPP` | `Performance` | EPP value used for the Custom profile. |
| `profile_performance_epp` | `CPUEPP` | `Performance` | EPP value used for the Performance profile. |
| `ac_profile_tunings` | map of `PlatformProfile` to `Tuning` | `{}` | Per-profile PPT tuning groups used on AC power. |
| `dc_profile_tunings` | map of `PlatformProfile` to `Tuning` | `{}` | Per-profile PPT tuning groups used on battery. |
| `armoury_settings` | map of `FirmwareAttribute` to `i32` | `{}` | Persisted firmware-attribute values applied at startup. |
| `screenpad_gamma` | `Option<f32>` | omitted (`None`) | ScreenPad gamma. `None` behaves as `1.0` (linear). |
| `screenpad_sync_primary` | `Option<bool>` | omitted (`None`) | Sync ScreenPad brightness with the primary display. `None` behaves as disabled. |
| `xgm_led_enabled` | `Option<bool>` | omitted (`None`) | Persisted XG Mobile LED state: `None` = never set, `Some(false)` = off, `Some(true)` = on. |
| `last_power_plugged` | `u8` | not written | Runtime-only AC/battery state (`#[serde(skip)]`). Do not add it to the file. |

`PlatformProfile` values are `Balanced`, `Performance`, `Quiet`, `LowPower`, and `Custom`. Their numeric values are `Balanced = 0`, `Performance = 1`, `Quiet = 2`, `LowPower = 3`, and `Custom = 4`; the kernel string for `LowPower` is `low-power`. Profile names are parsed case-insensitively and ignore punctuation, so `low-power`, `low_power`, and `LowPower` all resolve to `LowPower`. `CPUEPP` values are `Default`, `Performance`, `BalancePerformance`, `BalancePower`, and `Power`. A `Tuning` value is `(enabled: bool, group: { ... })`, where `group` maps `FirmwareAttribute` variants to `i32` values. The RON key is the variant name, not the sysfs name. The example below is a fragment; replace the two tuning fields in your existing `asusd.ron` instead of copying it as the whole file:

```ron
(
    ac_profile_tunings: {
        Performance: (
            enabled: true,
            group: {
                PptPl1Spl: 80,
                PptPl2Sppt: 100,
            },
        ),
    },
    dc_profile_tunings: {
        Balanced: (
            enabled: false,
            group: {},
        ),
    },
)
```

The same variant names are used in `armoury_settings`, for example `armoury_settings: { PanelOverdrive: 1 }`. The lower-case names such as `ppt_pl1_spl` and `panel_overdrive` are the names accepted by `asusctl armoury`, not the RON keys. GPU attributes such as `DgpuDisable` are not restored from `armoury_settings`; set them with `asusctl armoury`.

> [!WARNING]
> `asusd.ron` is deserialized as one complete struct. Omitting a required field from the current format makes the whole file invalid; if it does not match a known older format either, `asusd` renames it to `asusd.ron-old` before writing a fresh default. Only `base_charge_control_end_threshold`, `screenpad_gamma`, `screenpad_sync_primary`, and `xgm_led_enabled` may be omitted; an omitted `base_charge_control_end_threshold` defaults to `0`, not `100`. `last_power_plugged` is skipped entirely and is never part of the file.

### Older formats

The loader tries the current format, then `Config611`, then `Config601`:

- `Config611` is the format before `screenpad_gamma`, `screenpad_sync_primary`, and `xgm_led_enabled` were added. A `Config611` file that omits `base_charge_control_end_threshold` is accepted as the current format, with the base limit set to `0`; the `Config611` conversion is not reached. Reapply the limit with `asusctl battery limit`.
- `Config601` additionally had `panel_od`, `boot_sound`, `mini_led_mode`, and the `ppt_pl1_spl`, `ppt_pl2_sppt`, `ppt_pl3_fppt`, `ppt_fppt`, `ppt_apu_sppt`, `ppt_platform_sppt`, `nv_dynamic_boost`, and `nv_temp_target` fields. These extra fields are not migrated; the old file is only used to recover the common fields. Use `asusctl armoury` to set the equivalent firmware attributes afterwards.
- `Config601` has no `profile_custom_epp`; for both older formats, migration copies the Custom EPP from `profile_performance_epp` (the `profile_custom_epp` field in `Config611` is ignored).

Migration is automatic and writes the new file. Do not add the old fields to a current `asusd.ron`; unknown fields are ignored and are dropped on the next write.

### Power commands

`ac_command` and `bat_command` are split on whitespace and executed directly, without a shell. Redirection, pipes, `&&`, environment-variable expansion, and quoting are not interpreted:

```ron
ac_command: "systemctl start my-ac.service",
bat_command: "systemctl stop my-ac.service",
```

If you need a shell, put the logic in a script and call the script with its absolute path.

The command is spawned, not waited on. `asusd` does not capture its output or exit status, and a missing binary is only logged; the daemon keeps running.

### Daemon-managed fields

`asusd` rewrites `asusd.ron` when state changes. Prefer the CLI for these fields, because manual edits can be overwritten:

| Field | Use instead |
|---|---|
| `charge_control_end_threshold`, `base_charge_control_end_threshold` | `asusctl battery limit` and `asusctl battery oneshot` |
| `ac_profile_tunings`, `dc_profile_tunings` | `asusctl profile tuning` and `asusctl armoury set` |
| `armoury_settings` | `asusctl armoury set` |
| `screenpad_gamma`, `screenpad_sync_primary` | `asusctl backlight --screenpad-gamma` and `--sync-screenpad-brightness` |
| `xgm_led_enabled` | `asusctl xgmled set` |

## Power Profiles Daemon

`asusd` manages the ACPI `platform_profile` interface and CPU EPP itself. Running another power daemon (`power-profiles-daemon`, `tuned`, or `tuned-ppd`) alongside it can cause races over the same sysfs files. Pick one owner.

> [!IMPORTANT]
> **Option 1: let `asusd` manage profiles.** Disable and mask the external daemon:
>
> ```bash
> sudo systemctl disable --now power-profiles-daemon.service
> sudo systemctl mask power-profiles-daemon.service
> ```
>
> If you use `tuned` instead:
>
> ```bash
> sudo systemctl mask --now tuned.service tuned-ppd.service
> ```
>
> **Option 2: keep the external daemon.** Disable `asusd`'s profile management by setting these fields to `false` in `/etc/asusd/asusd.ron`:
>
> ```ron
> change_platform_profile_on_ac: false,
> change_platform_profile_on_battery: false,
> platform_profile_linked_epp: false,
> ```
>
> These are fields inside the top-level `asusd.ron` struct, not a complete file.

> [!NOTE]
> KDE Plasma's PowerDevil can respawn `power-profiles-daemon` through D-Bus activation even after the unit has been disabled. Mask the unit as shown above if you want `asusd` to be the only owner. [INFERENCE]

Fan-curve initialization can still switch profiles when `fan_curves.ron` is missing or empty, then restore the active profile. This is temporary and does not hand profile ownership to `asusd`.

The relevant defaults are `change_platform_profile_on_ac: true`, `change_platform_profile_on_battery: true`, and `platform_profile_linked_epp: true`.

A few details matter when the kernel exposes a different profile set:

- `LowPower` uses `profile_quiet_epp`, the same EPP value as `Quiet`.
- If the requested EPP value is not in the kernel's available list and the CPU governor is not already `powersave`, `asusd` switches the governor to `powersave` and retries the EPP write.
- If `platform_profile_on_ac` or `platform_profile_on_battery` names a profile the kernel does not expose, `asusd` substitutes the equivalent name: `Quiet` becomes `LowPower` and `LowPower` becomes `Quiet` when only the other one is available. The stored value in `asusd.ron` is rewritten to the substituted name so the next AC/battery transition uses it directly.

`asusctl profile next` follows a fixed order: `Balanced` → `Performance` → `LowPower` if the kernel reports it, otherwise `Quiet` → `Balanced`. From `Quiet`, `LowPower`, or `Custom` it returns to `Balanced`.

## Fan curves

Fan curves are stored in `/etc/asusd/fan_curves.ron`. The file contains four profile lists:

```ron
(
    profiles: (
        balanced: [
            (
                fan: CPU,
                pwm: (3, 5, 8, 10, 79, 125, 143, 148),
                temp: (30, 49, 59, 69, 79, 89, 99, 100),
                enabled: true,
            ),
        ],
        performance: [],
        quiet: [],
        custom: [],
    ),
)
```

Each `CurveData` has:

| Field | Description |
|---|---|
| `fan` | `CPU`, `GPU`, or `MID`. |
| `pwm` | Eight fan-power values, `0-255`. |
| `temp` | Eight temperature points in degrees Celsius. |
| `enabled` | Whether this curve is written to the EC for the profile. |

`LowPower` has no list of its own: it uses the `quiet` list. The `custom` list is used by the `Custom` profile.

The CLI accepts the same curve as eight comma-separated points:

```text
30c:1%,49c:2%,59c:3%,69c:4%,79c:31%,89c:49%,99c:56%,100c:58%
```

- Exactly eight points are required. Fewer points are rejected; more than eight is not supported (the parser indexes fixed eight-element arrays).
- The separator may be `c` or `:`.
- With `%`, fan power is a percentage (`0-100`); without `%`, it is the raw PWM range (`0-255`).
- Do not mix percent and raw values in one curve. Once a `%` is seen, the remaining values are parsed as percentages.
- Temperature and fan power must be non-decreasing along the curve. Equal adjacent values are allowed.
- Temperatures above 100 °C are not recommended.
- A curve parsed from the CLI starts with `enabled: false`. Use `--enable-fan-curve` or `--enable-fan-curves` to activate it.

`FanCurveConfig::new()` starts with empty profiles. `asusd` seeds the file when `fan_curves.ron` does not exist or the `balanced` list is empty. It switches to each supported platform profile and reads the current EC defaults into the file; the EC defaults are not hard-coded. `asusctl fan-curve --default` re-reads the defaults for the active profile.

The `current` field is runtime-only (`#[serde(skip)]`) and records the active profile; do not add it to the file.

Two write-order details are handled by `asusd`:

- When a profile is written to the EC, disabled curves are written first and enabled curves last. The kernel resets all curves when one is disabled, so the enabled set must be the final write.
- After a fan-curve write, `asusd` re-applies the PPT tuning values for the active profile. The EC fan-mode reset can clear them, so the re-apply keeps the configured power limits in effect.

`save_fan_curve` only replaces an existing entry for the same fan; it does not append a new fan to a profile. If a fan is missing from a profile list, setting a curve for it has no effect; use `--default` to re-seed the list from the EC.

> [!TIP]
> Prefer the CLI over editing `fan_curves.ron` directly. See [fan-curve](../usage/asusctl.md#fan-curve) for the commands and options.

## AniMe Matrix

`/etc/asusd/anime.ron` controls the AniMe Matrix display and the sequences used for system events. A freshly created file (from `AniMeConfig::create_default()`) contains these sample actions:

```ron
(
    system: [],
    boot: [
        ImageAnimation(
            file: "/usr/share/asusd/anime/custom/sonic-run.gif",
            scale: 0.9,
            angle: 0.65,
            translation: (0.0, 0.0),
            time: Fade((
                fade_in: (secs: 2, nanos: 0),
                show_for: Some((secs: 2, nanos: 0)),
                fade_out: (secs: 2, nanos: 0),
            )),
            brightness: 1.0,
        ),
    ],
    wake: [
        ImageAnimation(
            file: "/usr/share/asusd/anime/custom/sonic-run.gif",
            scale: 0.9,
            angle: 0.65,
            translation: (0.0, 0.0),
            time: Fade((
                fade_in: (secs: 2, nanos: 0),
                show_for: Some((secs: 2, nanos: 0)),
                fade_out: (secs: 2, nanos: 0),
            )),
            brightness: 1.0,
        ),
    ],
    shutdown: [
        ImageAnimation(
            file: "/usr/share/asusd/anime/custom/sonic-wait.gif",
            scale: 0.9,
            angle: 0.0,
            translation: (3.0, 2.0),
            time: Infinite,
            brightness: 1.0,
        ),
    ],
    display_enabled: true,
    display_brightness: Med,
    builtin_anims_enabled: true,
    off_when_unplugged: true,
    off_when_suspended: true,
    off_when_lid_closed: true,
    brightness_on_battery: Low,
    builtin_anims: (
        boot: GlitchConstruction,
        awake: BinaryBannerScroll,
        sleep: BannerSwipe,
        shutdown: GlitchOut,
    ),
)
```

| Field | Default | Description |
|---|---|---|
| `system` | `[]` | Actions played by the `run_main_loop` D-Bus method. This is the base system sequence used by tools; it is not the boot animation. |
| `boot` | `[]` in `Default`; one sample action in a new file | Actions played while booting. |
| `wake` | `[]` in `Default`; one sample action in a new file | Actions played when waking from suspend. |
| `shutdown` | `[]` in `Default`; one sample action in a new file | Actions played during shutdown. |
| `display_enabled` | `true` | Enable the display. |
| `display_brightness` | `Med` | Global brightness: `Off`, `Low`, `Med`, or `High`. |
| `builtin_anims_enabled` | `true` | Use the built-in animations instead of the custom `boot`/`wake`/`shutdown` actions. |
| `off_when_unplugged` | `true` | Turn the display off when external power is unplugged. |
| `off_when_suspended` | `true` | Turn the display off when the laptop suspends. |
| `off_when_lid_closed` | `true` | Turn the display off when the lid is closed. |
| `brightness_on_battery` | `Low` | Brightness used on battery power: `Off`, `Low`, `Med`, or `High`. |
| `builtin_anims` | see below | Built-in animation selection for each power state. |

`builtin_anims` accepts:

| Field | Values | Default |
|---|---|---|
| `boot` | `GlitchConstruction`, `StaticEmergence` | `GlitchConstruction` |
| `awake` | `BinaryBannerScroll`, `RogLogoGlitch` | `BinaryBannerScroll` |
| `sleep` | `BannerSwipe`, `Starfield` | `BannerSwipe` |
| `shutdown` | `GlitchOut`, `SeeYa` | `GlitchOut` |

`AniMeConfig::default()` has empty action vectors; `create_default()`, used when the file is first created, seeds the sample actions shown above. The `anime_type` field is runtime-only (`#[serde(skip)]`), and the daemon decodes actions into `AniMeConfigCached` in memory; neither is written to the file. See [AniMe sequences](anime-sequences.md) for the action format.

## Aura

`/etc/asusd/aura_<product_id>.ron` is generated by `asusd` from `/usr/share/asusd/aura_support.ron` and the detected USB product ID. It stores the built-in Aura modes, the current mode, brightness, multizone state, and per-zone power settings. The `led_type`, `support_data`, and `per_key_mode_active` fields are runtime-only and are not written to the file.

A minimal generated file looks like this:

```ron
(
    config_name: "aura_19b6.ron",
    brightness: Med,
    current_mode: Static,
    builtins: {
        Static: (
            mode: Static,
            zone: None,
            colour1: (r: 166, g: 0, b: 0),
            colour2: (r: 0, g: 0, b: 0),
            speed: Med,
            direction: Right,
        ),
    },
    multizone_on: false,
    enabled: (
        states: [
            (zone: Keyboard, boot: true, awake: true, sleep: true, shutdown: true),
        ],
    ),
)
```

| Field | Type | Default | Description |
|---|---|---|---|
| `config_name` | `String` | `aura_<product_id>.ron` | File name. If empty, the loader falls back to `aura.ron`. |
| `ally_fix` | `Option<bool>` | omitted (`None`) | Daemon-managed Ally power-reset marker. The loader resets it to `None`; `fix_ally_power` sets it to `Some(true)` after the reset. Do not edit. |
| `brightness` | `LedBrightness` | `Med` | Keyboard brightness: `Off`, `Low`, `Med`, or `High`. |
| `current_mode` | `AuraModeNum` | `Static` | Active built-in mode. |
| `builtins` | map of `AuraModeNum` to `AuraEffect` | seeded per supported mode | One effect per basic mode reported by the support database. |
| `multizone` | `Option<map of AuraModeNum to Vec<AuraEffect>>` | omitted (`None`) | Per-zone effects. Omitted when the keyboard has no zones. |
| `multizone_on` | `bool` | `false` | Whether the multizone set is active. |
| `enabled` | `LaptopAuraPower` | one state per supported power zone | Per-zone power states. The inner `states` list holds `AuraPowerState` values. |
| `led_type` | `AuraDeviceType` | runtime | `#[serde(skip)]`; detected from the product ID. |
| `support_data` | `LedSupportData` | runtime | `#[serde(skip)]`; support database entry. |
| `per_key_mode_active` | `bool` | runtime | `#[serde(skip)]`; whether direct per-key addressing is in use. |

An `AuraEffect` has these fields:

| Field | Type | Default | Description |
|---|---|---|---|
| `mode` | `AuraModeNum` | `Static` | Effect mode. |
| `zone` | `AuraZone` | `None` | Target zone; `None` means the whole keyboard. |
| `colour1` | `Colour` | `(166, 0, 0)` | Primary colour. |
| `colour2` | `Colour` | `(0, 0, 0)` | Secondary colour for modes that use two colours. |
| `speed` | `Speed` | `Med` | Animation speed: `Low`, `Med`, or `High`. |
| `direction` | `Direction` | `Right` | Animation direction: `Right`, `Left`, `Up`, or `Down`. |

The enum values are:

| Enum | Values |
|---|---|
| `LedBrightness` | `Off`, `Low`, `Med` (default), `High` |
| `AuraModeNum` | `Static` (default), `Breathe`, `RainbowCycle`, `RainbowWave`, `Star`, `Rain`, `Highlight`, `Laser`, `Ripple`, `Pulse`, `Comet`, `Flash` |
| `AuraZone` | `None` (default), `Key1`, `Key2`, `Key3`, `Key4`, `Logo`, `BarLeft`, `BarRight` |
| `Speed` | `Low`, `Med` (default), `High` |
| `Direction` | `Right` (default), `Left`, `Up`, `Down` |
| `PowerZones` | `Logo`, `Keyboard` (default), `Lightbar`, `Lid`, `RearGlow`, `KeyboardAndLightbar`, `Ally`, `None` |

`AuraPowerState` has `zone`, `boot`, `awake`, `sleep`, and `shutdown`. All four boolean states default to `true` for each zone the support database reports.

On startup, `load_and_update_config` merges the file with the support database: new supported modes are added, stored values for existing modes are kept, multizone entries whose mode is no longer supported are filtered out, and the file is rewritten. This is why the file can change after a kernel or support-data update.

Do not edit this file by hand. Use `asusctl aura` to change the built-in modes, brightness, and power zones. See the [supported laptops list](https://github.com/OpenGamingCollective/asusctl#supported-laptops) for model coverage, and `asusctl info --show-supported` for the modes and zones detected on your machine.

## SCSI LEDs

`/etc/asusd/scsi.ron` stores the SCSI drive LED state on laptops that expose those LEDs. It is read at startup; restart `asusd.service` after editing. The file is a single `ScsiConfig`:

```ron
(
    enabled: true,
    current_mode: Static,
    modes: {
        Static: (
            mode: Static,
            speed: Med,
            direction: Forward,
            colour1: (r: 166, g: 0, b: 0),
            colour2: (r: 0, g: 0, b: 0),
            colour3: (r: 166, g: 0, b: 0),
            colour4: (r: 0, g: 0, b: 0),
        ),
    },
)
```

| Field | Type | Default | Description |
|---|---|---|---|
| `enabled` | `bool` | `true` | Enable the SCSI drive LEDs. |
| `current_mode` | `AuraMode` | `Static` | Active mode. |
| `modes` | map of `AuraMode` to `AuraEffect` | one entry per mode | Stored effect for each mode. |
| `dev_type` | `AuraDeviceType` | runtime | `#[serde(skip)]`; detected device type. |

The example above shows one entry. A freshly created `scsi.ron` contains an entry for every mode: `Off`, `Static`, `Breathe`, `Flashing`, `RainbowCycle`, `RainbowWave`, `RainbowCycleBreathe`, `ChaseFade`, `RainbowCycleChaseFade`, `Chase`, `RainbowCycleChase`, `RainbowCycleWave`, `RainbowPulseChase`, `RandomFlicker`, and `DoubleFade`.

Each `AuraEffect` has `mode`, `speed`, `direction`, and four colours:

| Field | Type | Default | Description |
|---|---|---|---|
| `mode` | `AuraMode` | `Static` | Effect mode. |
| `speed` | `Speed` | `Med` | `Slowest`, `Slow`, `Med`, `Fast`, or `Fastest`. |
| `direction` | `Direction` | `Forward` | `Forward` or `Reverse`. |
| `colour1` | `Colour` | `(166, 0, 0)` | First colour. |
| `colour2` | `Colour` | `(0, 0, 0)` | Second colour. |
| `colour3` | `Colour` | `(166, 0, 0)` | Third colour. |
| `colour4` | `Colour` | `(0, 0, 0)` | Fourth colour. |

Use `asusctl scsi` to change the mode, speed, direction, and colours; see [scsi](../usage/asusctl.md#scsi). The daemon writes the file when a mode is saved.

## Slash LED bar

`/etc/asusd/slash.ron` stores the Slash LED bar state on supported laptops that have one. It is read at startup; restart `asusd.service` after editing:

```ron
(
    enabled: true,
    brightness: 255,
    display_interval: 0,
    display_mode: Bounce,
    show_on_boot: true,
    show_on_shutdown: true,
    show_on_sleep: true,
    show_on_battery: true,
    show_battery_warning: true,
    show_on_lid_closed: true,
)
```

| Field | Type | Default | Description |
|---|---|---|---|
| `enabled` | `bool` | `true` | Enable the Slash LED bar. |
| `brightness` | `u8` | `255` | Brightness, `0-255`. |
| `display_interval` | `u8` | `0` | Animation interval. The CLI documents `0-5`; the file stores a `u8`. |
| `display_mode` | `SlashMode` | `Bounce` | Animation mode. |
| `show_on_boot` | `bool` | `true` | Show the animation on boot. |
| `show_on_shutdown` | `bool` | `true` | Show the animation on shutdown. |
| `show_on_sleep` | `bool` | `true` | Show the animation on sleep. |
| `show_on_battery` | `bool` | `true` | Show the animation on battery power. |
| `show_battery_warning` | `bool` | `true` | Show the low-battery warning animation. |

`SlashMode` values are `Static`, `Bounce`, `Slash`, `Loading`, `BitStream`, `Transmission`, `Flow`, `Flux`, `Phantom`, `Spectrum`, `Hazard`, `Interfacing`, `Ramp`, `GameOver`, `Start`, and `Buzzer`.

> [!NOTE]
> `show_on_lid_closed` is stored in `slash.ron` but is not exposed by `asusctl slash set`. To change it, stop `asusd.service`, edit the field, and start the service again. The other fields are available through `asusctl slash set`; see [slash](../usage/asusctl.md#slash).

## BIOS and Armoury

Firmware settings exposed by the `asus-armoury` kernel driver are available through `asusctl armoury`:

```bash
asusctl armoury list
asusctl armoury get dgpu_disable
asusctl armoury set dgpu_disable 1
asusctl armoury set dgpu_disable -- -1   # reset to the firmware default
```

See [armoury](../usage/asusctl.md#armoury) for the full command reference. PPT attributes are only applied while profile tuning is enabled. If tuning is disabled, `asusd` rejects the write with an error; enable tuning first with `asusctl profile tuning true`. The value is then stored in the active AC or DC tuning group and applied immediately.

Writing `nv_dynamic_boost`, `nv_temp_target`, or `nv_tgp` also runs `systemctl try-restart nvidia-powerd.service` so the daemon re-reads the new limits.

`asusctl armoury list` shows the attributes the driver exposes. Each attribute has a name, a current value, a default value, possible values, and optional minimum and maximum metadata. Values are one of `Integer`, `String`, `EnumInt`, `EnumStr`, or `None`. `asusctl armoury get` prints the current value; `asusctl armoury set <name> <value>` writes it. A value of `-1` is replaced with the attribute's `default_value` before writing.

The attribute type controls when a write takes effect:

| Type | Behaviour |
|---|---|
| `Immediate` | Written to sysfs and persisted in `armoury_settings`; re-applied at startup and reload. |
| `Bios` | Uses the same persistence path as `Immediate`; the type marks a BIOS-owned setting. |
| `Ppt` | Stored in the active profile's AC or DC tuning group. Applied only when tuning is enabled. Not stored in `armoury_settings`. |
| `Gpu` | The write is queued in memory and applied at shutdown by `asus-shutdown`; not persisted; requires a reboot. |
| `ReadOnly` | Writes are rejected. Stale persisted values are removed. |
| `Norestore` | Written synchronously but never persisted or re-applied. Stale persisted values are removed. |

The attributes known to `asusd` are:

| `asusctl` name | RON variant | Type |
|---|---|---|
| `apu_mem` | `ApuMem` | `Norestore` |
| `cores_performance` | `CoresPerformance` | `Immediate` |
| `cores_efficiency` | `CoresEfficiency` | `Immediate` |
| `ppt_pl1_spl` | `PptPl1Spl` | `Ppt` |
| `ppt_pl2_sppt` | `PptPl2Sppt` | `Ppt` |
| `ppt_pl3_fppt` | `PptPl3Fppt` | `Ppt` |
| `ppt_fppt` | `PptFppt` | `Ppt` |
| `ppt_apu_sppt` | `PptApuSppt` | `Ppt` |
| `ppt_platform_sppt` | `PptPlatformSppt` | `Ppt` |
| `nv_dynamic_boost` | `NvDynamicBoost` | `Ppt` |
| `nv_temp_target` | `NvTempTarget` | `Ppt` |
| `nv_base_tgp` | `DgpuBaseTgp` | `ReadOnly` |
| `nv_tgp` | `DgpuTgp` | `Ppt` |
| `charge_mode` | `ChargeMode` | `ReadOnly` |
| `boot_sound` | `BootSound` | `Bios` |
| `mcu_powersave` | `McuPowersave` | `Immediate` |
| `panel_overdrive` | `PanelOverdrive` | `Immediate` |
| `panel_hd_mode` | `PanelHdMode` | `Immediate` |
| `egpu_connected` | `EgpuConnected` | `Gpu` |
| `egpu_enable` | `EgpuEnable` | `Gpu` |
| `dgpu_disable` | `DgpuDisable` | `Gpu` |
| `gpu_mux_mode` | `GpuMuxMode` | `Gpu` |
| `mini_led_mode` | `MiniLedMode` | `Immediate` |
| `screen_auto_brightness` | `ScreenAutoBrightness` | `Immediate` |
| `pending_reboot` | `PendingReboot` | not listed |
| `none` | `None` | sentinel for unknown names |

`pending_reboot` is present in the enum but is skipped when the attribute list is built, so it does not appear in `asusctl armoury list`. Not every laptop exposes every attribute; use `asusctl armoury list` for the actual set.

GPU switching uses the `dgpu_disable` and `gpu_mux_mode` attributes. Both are `Gpu`-type: the write is queued and applied at shutdown, so a reboot is required; see [GPU Switching](../faq/gpu-switching.md). BIOS settings that are not exposed by the driver must be changed in the UEFI setup.

## Support introspection

The old support controller is commented out in the daemon, so there is no separate support D-Bus interface to query. Use:

```bash
asusctl info
asusctl info --show-supported
```

`--show-supported` prints the supported core functions, platform properties, keyboard brightness levels, Aura modes, Aura zones, and Aura power zones for the current machine.
