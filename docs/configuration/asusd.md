# asusd Configuration

`asusd` is the system daemon. Its configuration lives in `/etc/asusd/`, is owned by root, and is written by the daemon as state changes. Edit these files with `sudo`. Back up the directory before editing:

```bash
sudo cp -a /etc/asusd "/etc/asusd.bak.$(date +%F-%H%M%S)"
```

## Configuration files

| File | Purpose | Reload behaviour |
|---|---|---|
| `asusd.ron` | Platform profiles, battery charging, power commands, EPP, tuning, and Armoury settings. | Watched with inotify; changes are reloaded while the daemon runs. Only the charge limit and `platform_profile_linked_epp` are applied on reload; `armoury_settings` and other hardware settings are applied at startup, so use `asusctl` or restart `asusd.service` and `asus-shutdown.service`. |
| `fan_curves.ron` | Fan curves for the `balanced`, `performance`, `quiet`, and `custom` profiles. | Read at startup; restart `asusd.service` and `asus-shutdown.service` after editing. |
| `anime.ron` | AniMe Matrix display state and the system/boot/wake/shutdown sequences. | Read at startup; restart `asusd.service` and `asus-shutdown.service` after editing. |
| `scsi.ron` | SCSI drive LED state and the per-mode effects. | Read at startup; restart `asusd.service` and `asus-shutdown.service` after editing. |
| `slash.ron` | Slash LED bar state and the per-event display flags. | Read at startup; restart `asusd.service` and `asus-shutdown.service` after editing. |
| `aura_<product_id>.ron` | Generated Aura state for the detected keyboard. | Generated by `asusd`; do not edit by hand. |

> [!WARNING]
> Every restart in the table above clears the in-memory GPU queue. A GPU change queued with `asusctl armoury set` before the restart is lost and will not apply at shutdown. Queue it again after the services are back up.

The file is a single RON struct. A complete default file looks like this:

`PlatformProfile` values are `Balanced`, `Performance`, `Quiet`, `LowPower`, and `Custom`. Their numeric values are `Balanced = 0`, `Performance = 1`, `Quiet = 2`, `LowPower = 3`, and `Custom = 4`; the kernel string for `LowPower` is `low-power`. In RON, use the exact variant name `LowPower`; `low_power` and `low-power` are not accepted. On the command line, profile names are parsed case-insensitively and ignore punctuation, so `low-power`, `low_power`, and `LowPower` all resolve to `LowPower`. `CPUEPP` values are `Default`, `Performance`, `BalancePerformance`, `BalancePower`, and `Power`. A `Tuning` value is `(enabled: bool, group: { ... })`, where `group` maps `FirmwareAttribute` variants to `i32` values. The RON key is the variant name, not the sysfs name. The example below is a fragment; replace the two tuning fields in your existing `asusd.ron` instead of copying it as the whole file:

```ron
(
    ac_profile_tunings: {
        Performance: (
            enabled: true,
            group: {
                PptPl1Spl: 80,
                PptPl2Sppt: 100,
            },
        ),
    },
    dc_profile_tunings: {
        Balanced: (
            enabled: false,
            group: {},
        ),
    },
)
```

The same variant names are used in `armoury_settings`, for example `armoury_settings: { PanelOverdrive: 1 }`. The lower-case names such as `ppt_pl1_spl` and `panel_overdrive` are the names accepted by `asusctl armoury`, not the RON keys. GPU attributes such as `DgpuDisable` are not restored from `armoury_settings`; set them with `asusctl armoury`.

> [!WARNING]
> `asusd.ron` is deserialized as one complete struct. Omitting a required field from the current format makes the whole file invalid; if it does not match a known older format either, `asusd` renames it to `asusd.ron-old` before writing a fresh default. Only `base_charge_control_end_threshold`, `screenpad_gamma`, `screenpad_sync_primary`, and `xgm_led_enabled` may be omitted; an omitted `base_charge_control_end_threshold` defaults to `0`, not `100`. `last_power_plugged` is skipped entirely and is never part of the file.

> [!WARNING]
> Before starting a one-shot charge, record the previous limit with `asusctl battery info`. Editing `asusd.ron` while a one-shot charge is active can reset `base_charge_control_end_threshold` to `0`, so the previous limit is not restored. Stop `asusd.service` before editing the file. After starting `asusd.service` and `asus-shutdown.service` again, reapply the previous limit with `asusctl battery limit <previous-limit>`. This ends the one-shot charge.

### Older formats

The loader tries the current format, then `Config611`, then `Config601`:

- `Config611` is the format before `screenpad_gamma`, `screenpad_sync_primary`, and `xgm_led_enabled` were added. A `Config611` file that omits `base_charge_control_end_threshold` is accepted as the current format, with the base limit set to `0`; the `Config611` conversion is not reached. Reapply the limit with `asusctl battery limit <previous-limit>`.
- `Config601` additionally had `panel_od`, `boot_sound`, `mini_led_mode`, and the `ppt_pl1_spl`, `ppt_pl2_sppt`, `ppt_pl3_fppt`, `ppt_fppt`, `ppt_apu_sppt`, `ppt_platform_sppt`, `nv_dynamic_boost`, and `nv_temp_target` fields. These extra fields are not migrated; the old file is only used to recover the common fields. Use `asusctl armoury` to set the equivalent firmware attributes afterwards.
- `Config601` has no `profile_custom_epp`; for both older formats, migration copies the Custom EPP from `profile_performance_epp` (the `profile_custom_epp` field in `Config611` is ignored).

Migration is automatic and writes the new file. Do not add the old fields to a current `asusd.ron`; unknown fields are ignored and are dropped on the next write.

### Power commands

`ac_command` and `bat_command` are split on whitespace and executed directly, without a shell. Redirection, pipes, `&&`, environment-variable expansion, and quoting are not interpreted:

```ron
ac_command: "systemctl start my-ac.service",
bat_command: "systemctl stop my-ac.service",
```

If you need a shell, put the logic in a script and call the script with its absolute path.

The command is spawned, not waited on. `asusd` does not capture its output or exit status, and a missing binary is only logged; the daemon keeps running.

### Daemon-managed fields

`asusd` rewrites `asusd.ron` when state changes. Prefer the CLI for these fields, because manual edits can be overwritten:

| Field | Use instead |
|---|---|
| `charge_control_end_threshold`, `base_charge_control_end_threshold` | `asusctl battery limit <percentage>` and `asusctl battery oneshot [<percentage>]` |
| `ac_profile_tunings`, `dc_profile_tunings` | `asusctl profile tuning` and `asusctl armoury set` |
| `armoury_settings` | `asusctl armoury set` |
| `screenpad_gamma`, `screenpad_sync_primary` | `asusctl backlight --screenpad-gamma` and `--sync-screenpad-brightness` |
| `xgm_led_enabled` | `asusctl xgmled set` |

## Power Profiles Daemon

`asusd` manages the ACPI `platform_profile` interface and CPU EPP itself. Running another power daemon (`power-profiles-daemon`, `tuned`, or `tuned-ppd`) alongside it can cause races over the same sysfs files. Pick one owner.

> [!IMPORTANT]
> **Option 1: let `asusd` manage profiles.** Disable and mask the external daemon:
>
> ```bash
> sudo systemctl disable --now power-profiles-daemon.service
> sudo systemctl mask power-profiles-daemon.service
> ```
>
> If you use `tuned` instead:
>
> ```bash
> sudo systemctl mask --now tuned.service tuned-ppd.service
> ```
>
> **Option 2: keep the external daemon.** Disable `asusd`'s profile management by setting these fields to `false` in `/etc/asusd/asusd.ron`:
>
> ```ron
> change_platform_profile_on_ac: false,
> change_platform_profile_on_battery: false,
> platform_profile_linked_epp: false,
> ```
>
> These are fields inside the top-level `asusd.ron` struct, not a complete file.

> [!NOTE]
> KDE Plasma's PowerDevil may respawn `power-profiles-daemon` through D-Bus activation even after the unit has been disabled. Mask the unit as shown above if you want `asusd` to be the only owner.

Fan-curve initialization can still switch profiles when `fan_curves.ron` is missing or empty, then restore the active profile. This is temporary and does not hand profile ownership to `asusd`.

The relevant defaults are `change_platform_profile_on_ac: true`, `change_platform_profile_on_battery: true`, and `platform_profile_linked_epp: true`.

A few details matter when the kernel exposes a different profile set:

- `LowPower` uses `profile_quiet_epp`, the same EPP value as `Quiet`.
- If the requested EPP value is not in the kernel's available list and the CPU governor is not already `powersave`, `asusd` switches the governor to `powersave` and retries the EPP write.
- If `platform_profile_on_ac` or `platform_profile_on_battery` names a profile the kernel does not expose, `asusd` substitutes the equivalent name: `Quiet` becomes `LowPower` and `LowPower` becomes `Quiet` when only the other one is available. The stored value in `asusd.ron` is rewritten to the substituted name so the next AC/battery transition uses it directly.

`asusctl profile next` follows a fixed order: `Balanced` → `Performance` → `LowPower` if the kernel reports it, otherwise `Quiet` → `Balanced`. From `Quiet`, `LowPower`, or `Custom` it returns to `Balanced`.

## Fan curves

Fan curves are stored in `/etc/asusd/fan_curves.ron`. The file contains four profile lists:

```ron
(
    profiles: (
        balanced: [
            (
                fan: CPU,
                pwm: (3, 5, 8, 10, 79, 125, 143, 148),
                temp: (30, 49, 59, 69, 79, 89, 99, 100),
                enabled: true,
            ),
        ],
        performance: [],
        quiet: [],
        custom: [],
    ),
)
```

The example is illustrative. Keep your existing fan and profile lists, including the `balanced` list; `asusd` seeds the file from the EC only when the file is missing or `balanced` is empty.

Each `CurveData` has:

| Field | Description |
|---|---|
| `fan` | `CPU`, `GPU`, or `MID`. |
| `pwm` | Eight fan-power values, `0-255`. |
| `temp` | Eight temperature points in degrees Celsius. |
| `enabled` | Whether this curve is written to the EC for the profile. |

`LowPower` has no list of its own: it uses the `quiet` list. The `custom` list is used by the `Custom` profile.

The CLI accepts the same curve as eight comma-separated points:

```text
30c:1%,49c:2%,59c:3%,69c:4%,79c:31%,89c:49%,99c:56%,100c:58%
```

- Exactly eight points are required. Fewer points are rejected; more than eight is not supported (the parser indexes fixed eight-element arrays).
- The separator may be `c` or `:`.
- With `%`, fan power is a percentage (`0-100`); without `%`, it is the raw PWM range (`0-255`).
- Do not mix percent and raw values in one curve. Once a `%` is seen, the remaining values are parsed as percentages.
- Temperature and fan power must be non-decreasing along the curve. Equal adjacent values are allowed.
- Temperatures above 100 °C are not recommended.
- A curve parsed from the CLI starts with `enabled: false`. Use `--enable-fan-curve` or `--enable-fan-curves` to activate it.

`FanCurveConfig::new()` starts with empty profiles. `asusd` seeds the file when `fan_curves.ron` does not exist or the `balanced` list is empty. It switches to each supported platform profile and reads the current EC defaults into the file; the EC defaults are not hard-coded. `asusctl fan-curve --default` re-reads the defaults for the active profile.

The `current` field is runtime-only (`#[serde(skip)]`) and records the active profile; do not add it to the file.

Two write-order details are handled by `asusd`:

- When a profile is written to the EC, disabled curves are written first and enabled curves last. The kernel resets all curves when one is disabled, so the enabled set must be the final write.
- After a fan-curve write, `asusd` re-applies the PPT tuning values for the active profile. The EC fan-mode reset can clear them, so the re-apply keeps the configured power limits in effect.

`save_fan_curve` only replaces an existing entry for the same fan; it does not append a new fan to a profile. If a fan is missing from a profile list, setting a curve for it has no effect. `asusctl fan-curve --default` resets the active profile, not the profile that is missing the fan; select the intended profile first. The reset replaces that profile's existing curves.

> [!TIP]
> Prefer the CLI over editing `fan_curves.ron` directly. See [fan-curve](../usage/asusctl.md#fan-curve) for the commands and options.

## Aura

`/etc/asusd/aura_<product_id>.ron` is generated by `asusd` from `/usr/share/asusd/aura_support.ron` and the detected USB product ID. It stores the built-in Aura modes, the current mode, brightness, multizone state, and per-zone power settings. The `led_type`, `support_data`, and `per_key_mode_active` fields are runtime-only and are not written to the file.

A minimal generated file looks like this:

```ron
(
    config_name: "aura_19b6.ron",
    brightness: Med,
    current_mode: Static,
    builtins: {
        Static: (
            mode: Static,
            zone: None,
            colour1: (r: 166, g: 0, b: 0),
            colour2: (r: 0, g: 0, b: 0),
            speed: Med,
            direction: Right,
        ),
    },
    multizone_on: false,
    enabled: (
        states: [
            (zone: Keyboard, boot: true, awake: true, sleep: true, shutdown: true),
        ],
    ),
)
```

## BIOS and Armoury

Firmware settings exposed by the `asus-armoury` kernel driver are available through `asusctl armoury`:

```bash
asusctl armoury list
asusctl armoury get dgpu_disable
asusctl armoury set dgpu_disable 1
asusctl armoury set dgpu_disable -- -1   # reset to the firmware default
```

See [armoury](../usage/asusctl.md#armoury) for the full command reference. PPT attributes are only applied while profile tuning is enabled. If tuning is disabled, `asusd` rejects the write with an error; enable tuning first with `asusctl profile tuning true`. On systems with fan-curve support, `asusctl profile tuning true` also requires an enabled custom fan curve in the active profile; otherwise `asusd` returns `Custom fan curve is required to enable profile tuning`. The value is then stored in the active AC or DC tuning group and applied immediately.

Writing `nv_dynamic_boost`, `nv_temp_target`, or `nv_tgp` also runs `systemctl try-restart nvidia-powerd.service` so the daemon re-reads the new limits.

`asusctl armoury list` shows the attributes the driver exposes. Each attribute has a name, a current value, a default value, possible values, and optional minimum and maximum metadata. Values are one of `Integer`, `String`, `EnumInt`, `EnumStr`, or `None`. `asusctl armoury get` prints the current value; `asusctl armoury set <name> <value>` writes it. A value of `-1` is replaced with the attribute's `default_value` before writing.

The attribute type controls when a write takes effect:

| Type | Behaviour |
|---|---|
| `Immediate` | Written to sysfs and persisted in `armoury_settings`; re-applied at startup and after profile or power-source changes. |
| `Bios` | Uses the same persistence path as `Immediate`; the type marks a BIOS-owned setting. |
| `Ppt` | Stored in the active profile's AC or DC tuning group. Applied only when tuning is enabled. Not stored in `armoury_settings`. |
| `Gpu` | The write is queued in memory and applied at shutdown by `asus-shutdown`; not persisted; requires a reboot. |
| `ReadOnly` | Writes are rejected. Stale persisted values are removed. |
| `Norestore` | Written synchronously but never persisted or re-applied. Stale persisted values are removed. |

The attributes known to `asusd` are:

{{#include ../generated/armoury-attributes.md}}

`pending_reboot` is present in the enum but is skipped when the attribute list is built, so it does not appear in `asusctl armoury list`. Not every laptop exposes every attribute; use `asusctl armoury list` for the actual set.

GPU switching uses the `dgpu_disable` and `gpu_mux_mode` attributes. Both are `Gpu`-type: the write is queued and applied at shutdown, so a reboot is required; see [GPU Switching](../faq/gpu-switching.md). BIOS settings that are not exposed by the driver must be changed in the UEFI setup.

## Support introspection

The old support controller is commented out in the daemon, so there is no separate support D-Bus interface to query. Use:

```bash
asusctl info
asusctl info --show-supported
```

`--show-supported` prints the supported core functions, platform properties, keyboard brightness levels, Aura modes, Aura zones, and Aura power zones for the current machine.
